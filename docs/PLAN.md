# ShibaPack 方案

跨平台软件安装包管理器。管理本机或 NAS 上的安装包文件，按软件、版本、文件三级整理，支持分类、收藏、智能分类、搜索、去重和一键运行。

## 已定的决策

| 项 | 决定 |
|---|---|
| 技术栈 | Tauri 2 + Rust + React 19 + TypeScript + Vite + Tailwind 4 |
| 存储 | 不用数据库。所有数据在用户指定的仓库根目录下，索引是根目录的 `software.json` |
| 多设备 | 不同步仓库文件夹，不做冲突合并 |
| 界面风格 | 参考 [Postflow](https://github.com/Wonvy/Postflow/)：深色默认、CSS 变量令牌、13px Inter、细分隔线、紧凑控件。只参考风格，不复制其源码（它是 GPL-3.0） |
| 强调色 | 默认蓝色，另有 4 种预设 |
| 布局 | 顶栏 + 侧栏（分类树）+ 中间栏（路由区）+ 详情栏 + 底栏，见下文 |

## 仓库文件夹

```
仓库根目录/                     在首次启动或设置的“仓库”页里指定
├─ software.json               唯一的索引：分类、软件、版本、文件、设置
├─ Visual Studio Code/         托管的安装包：软件名/版本号/原文件名
│  ├─ 1.96.2/
│  │  ├─ VSCodeUserSetup-x64-1.96.2.exe
│  │  └─ VSCode-darwin-universal.dmg
│  └─ 1.95.3/
│     └─ VSCodeUserSetup-x64-1.95.3.exe
├─ 7-Zip/
│  └─ 24.09/
│     └─ 7z2409-x64.exe
└─ .shibapack/
   ├─ backups/                 索引备份：最近 8 份，更早的每天一份、最多 14 天
   ├─ trash/                   删除的托管文件先移到这里，30 天后清除
   ├─ cache/                   可随时删除
   └─ logs/
```

- 平台、分类、收藏都只是索引里的字段，不体现在目录层级里，修改它们不会移动文件。
- 两种存储模式：**托管**把文件复制进仓库；**索引**只记录外部文件的绝对路径，不动原文件。
- 托管文件保留原文件名。软件名和版本号由文件夹表达，索引丢失时可据此重建。
- 仓库之外只有一个引导文件（系统应用配置目录下的 `config.json`），仅记录仓库根目录在哪。

## 索引格式（`software.json`）

```json
{
  "format": 1,
  "categories": [{ "id": "…", "name": "开发工具", "parentId": null, "color": "#5aa2ff", "icon": "code" }],
  "software": [
    {
      "id": "…",
      "name": "Visual Studio Code",
      "publisher": "Microsoft",
      "homepage": "",
      "note": "",
      "categoryId": "…",
      "starred": false,
      "icon": null,
      "defaultVersionId": "…",
      "addedAt": "2026-11-19T12:00:00+08:00",
      "versions": [
        {
          "id": "…",
          "version": "1.96.2",
          "note": "",
          "addedAt": "…",
          "files": [
            {
              "id": "…",
              "name": "VSCodeUserSetup-x64-1.96.2.exe",
              "platform": "windows",
              "arch": "x64",
              "size": 109051904,
              "sha256": "…",
              "storage": "managed",
              "path": "Visual Studio Code/1.96.2/VSCodeUserSetup-x64-1.96.2.exe",
              "addedAt": "…"
            }
          ]
        }
      ]
    }
  ],
  "summaries": {},
  "settings": { "theme": "system", "accent": "blue", "language": "zh-CN", "defaultStorage": "managed" }
}
```

托管文件的 `path` 是相对仓库根目录的路径（统一用 `/`），索引文件的 `path` 是绝对路径。

保存流程：写临时文件 → 重新读入校验 → 轮转备份 → 原子替换。读取时若索引损坏，改名为 `software.json.corrupt` 并从最新可用的备份恢复。

不丢数据的几条规矩（`store.rs`、`ops.rs`）：

- 只有内容坏了（不是合法 JSON、结构不对）才算损坏。读不出来（NAS 掉线、文件被占用）原样报错，不动原文件；引导页会说明上次的仓库为什么没打开，可以重试。
- `format` 比当前版本大的索引拒绝打开（`format_too_new`），也不当成损坏。**以后给索引加了旧版本丢掉会有损失的内容（记录、文件信息、新的枚举值）时，要把 `FORMAT` 加一**，否则旧版本读进来再存回去会把新内容丢掉。设置开关、简介译文这类丢了也无妨的字段不用加（`moveOnImport`、`translateSummaries`、`Summary.lang`、`Summary.translations` 就没加）。
- 每个命令都通过 `Repo::transact` 执行：先看索引文件的修改时间和大小，被别处改过（另一台电脑、手动编辑）就先读进来；命令失败时内存里的索引退回原样，半截的改动不会在下一次保存时被写进去。窗口回到前台时也会检查一次。
- 同一台电脑上只能开一个 ShibaPack（single-instance 插件）。多台电脑共用 NAS 上的仓库时不做合并，只保证不拿旧索引盖掉别人刚存的。
- 删除：先把托管文件移进回收站（有一个移不动就全部放回、什么都不改），再先备份后保存，保存失败再把文件放回去。别的记录还在用的文件不移走。
- 导入每登记 20 个文件或每 30 秒存一次索引，中途崩溃时已复制进仓库的文件大多已经登记。
- 导入分四步（`import.rs`）：算哈希、查重并决定放在哪、复制或移动、登记。桌面应用里只有第二、四步占着仓库，算哈希和复制几个 G 的文件时界面上的其他操作照常进行。导入可以取消（在两个文件之间停），同时只跑一批，导入中又拖进来的文件排队。
- 所有 `async` 命令都放到 `spawn_blocking` 的线程池里执行（`lib.rs` 的 `blocking`）：Tauri 默认把它们放在处理命令的异步线程上，那里只有 CPU 核数那么多线程，几个慢命令同时在跑会把别的命令连同插件一起卡住。
- 托管文件的路径按仓库内的相对路径解释，`..`、盘符一律丢掉；导入的外部索引要带 `format` 和 `software`，id 只能用字母、数字、`-`、`_`。
- 导出索引不能选仓库自己的 `software.json`。
- 下载：每次读数据最多等 60 秒；续传时带上次的 ETag / Last-Modified（If-Range），服务器上的文件换过就从头下。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 顶栏 52px（可拖下沿调高度）：Logo · ShibaPack   [ 搜索 ]        [+ 添加▾] │
├────────────┬───────────────────────────────┬─────────────────────────┤
│ 侧栏       │ 工具栏：标题 数量 │ [平台▾][安装状态▾] │ [视图▾][⊟] │ 详情栏（可收起）  │
│ 140–360px  │ （筛选在工具栏正中间）          │ 280–560px，默认 340      │
│ 可收起成   │ #/library    软件库            │ 头部：图标 名字 ☆ ⋯       │
│ 一列图标   │ #/installed  已安装软件        │ 简介                      │
│ 全部软件   │ 顶部 3px 导入进度条（可取消）  │ 安装状态 / 新版本         │
│ 已安装     │                               │ 版本与安装包              │
│ 收藏       │                               │ ▸ 更多信息（分类、在线源、 │
│ 有更新     │                               │   主页、备注，默认收起）   │
│ 分类树     │                               │                         │
│ 设置 [⇤]   │                               │                         │
│            ├───────────────────────────────┤                         │
│            │ 底栏 h-7（只在中间一栏）：● 状态 │                         │
│            │ 软件数 安装包数 总大小 路径 版本 │                         │
└────────────┴───────────────────────────────┴─────────────────────────┘
```

- 按功能分区：顶栏放全局的搜索、检查更新和“添加”（导入文件、导入文件夹、扫描建索引、整理根目录、从在线源添加都在这一个菜单里）；侧栏放导航和设置（仓库存储、备份都在设置窗口里）；列表工具栏左边是标题、正中间是筛选、右边是视图。
- 两条拖拽手柄调整侧栏和详情栏宽度，宽度和详情栏的开合存 localStorage（只和本机有关的界面状态）。
- 软件列表的“版本”列：在线源上有更新的版本时，版本号右边有一个小箭头。底栏的 ShibaPack 版本号同理。
- 字号最小 12px。
- macOS 使用系统的红黄绿按钮（左上角），不显示自绘的窗口按钮；Windows 和 Linux 为无边框窗口加自绘按钮。

## 代码结构

```
crates/core/      与界面无关的核心逻辑，可单独测试
  model.rs        数据结构
  store.rs        读写索引、备份、恢复、统计、校验
  identify.rs     从文件名识别软件名、版本、平台、架构
  import.rs       导入、去重、扫描目录
  ops.rs          软件、版本、文件、分类、收藏的增删改
  classify.rs     智能分类：按软件名、发布者、简介推荐分类
  ai.rs           AI 模型：OpenAI 兼容接口，写简介、推荐分类
  cleanup/        清理：规则（rules/*.toml）、路径变量、保护检查、扫描、删除、回收站、散落的安装包、清理记录
src-tauri/        桌面外壳：命令、事件、窗口
src/              React 前端
  lib/            类型、接口封装、状态、国际化、浏览器预览用的模拟后端
  components/     通用组件、顶栏、侧栏、详情栏、对话框
  views/          软件库、已安装、存储
```

### 在线更新

ShibaPack 会更新自己：启动几秒后（之后每六小时）到 GitHub 上查有没有新版本，有就在后台下载、验证签名并安装。

- macOS 和 Linux 上可以在应用运行时装好，右下角提示“重启后生效”，点“立即重启”即可。
- Windows 的安装程序必须先关掉应用，所以下载完成后提示“安装并重启”，点了才装。
- 设置里可以关掉“自动更新”，也可以手动“检查更新”。
- Linux 上只有 AppImage 能自我更新，deb 和 rpm 装的要重新下载安装包。

它依赖三样东西：

| 东西 | 在哪 |
|---|---|
| 更新清单的地址 | `src-tauri/tauri.conf.json` 的 `plugins.updater.endpoints`，指向 `github.com/Wonvy/ShibaPack` 最新 Release 里的 `latest.json` |
| 验证签名用的公钥 | 同一处的 `pubkey`，可以公开 |
| 给更新包签名的私钥 | 开发机上的 `~/.tauri/shibapack-updater.key`，**不进仓库**；CI 里是仓库的 Secret `TAURI_SIGNING_PRIVATE_KEY` |

私钥丢了就没法再给已安装的用户推送更新（只能让他们手动重装），所以要另外备份一份。

验证情况：

- 在本机做过一次真实的演练：把更新地址临时指向本机，旧版 0.1.0 启动后自己发现了 0.1.1，下载、验签、替换了应用包，版本号变成 0.1.1。
- 发布版的自检确认更新检查能连到 GitHub 上的正式地址（目前还没有发布过版本，所以查不到更新）。
- 没有验证的：通过 GitHub Releases 的完整发布流程一次也没走过；Windows 和 Linux 上的更新没有试过。

### AI 模型

参考 Postflow 的思路（只参考做法，代码是新写的；Postflow 是 GPL-3.0）：只用各家都提供的 OpenAI 兼容接口，从这台电脑直接请求用户选的服务。

| 项 | 说明 |
|---|---|
| 设置 | 设置里的“AI 模型”：选服务（DeepSeek、通义千问、Kimi、智谱 GLM、硅基流动、OpenAI、Gemini、OpenRouter、Ollama、LM Studio，或自定义地址）、填 API Key、选模型（可以从服务的模型列表里取）、测试连接。地址和模型存在 `software.json` 的 `settings.ai` 里，跟着仓库走；没加 `FORMAT`，旧版本读进来丢掉也只是要重新设置 |
| API Key | 只存在每台电脑的系统钥匙串里（macOS 钥匙串、Windows 凭据管理器、Linux Secret Service，`keyring` 库），按接口地址存，不进仓库文件夹。换一台电脑要重新填。Ollama、LM Studio 这类本机服务不需要密钥 |
| 写简介 | 详情栏的简介下面有“AI 写简介”（没有简介时）和“用 AI 重写”（鼠标停在简介上时）；软件的右键菜单、多选面板里也有，多个时一个一个写，最后汇总。简介用界面语言写，存进 `summaries`，来源记成 `AI · 模型名`，下面注明“由 AI 生成，可能有误”。发给模型的是软件名、发布者、主页、安装包文件名和联网取到的简介；模型不认识这个软件时回答 UNKNOWN，界面提示“AI 不认识这个软件”，不编一段 |
| 智能分类 | 设置好 AI 时，智能分类的预览窗口默认用 AI 判断，右上角可以换回内置规则。每次 30 个软件一批，带上分类树（编成 c1、c2……）和每个软件现在的分类；后面的批次会看到前面建议过的新分类名，免得同一类起出几个名字。已经在合适分类（含其下级）里的保持不动；说要新建的分类其实已经有了就用已有的。每行显示 AI 给的一句依据。关掉窗口或换回规则时，后面几批不再请求 |
| 请求细节 | 默认带温度、要求输出 JSON、让模型别先“思考”（各家参数不同，按预设或地址认）；服务不认这些参数回 400 时全去掉重试一次，并在这次运行里记住这个模型。不设输出上限，免得会思考的模型把回答截断。回答开头的 `<think>…</think>` 去掉。错误按状态码和服务原话归成密钥不对、余额不足、模型不存在、地址不对（少了或多了 `/v1`）、限流、超时等，界面显示对应的提示 |

验证情况：核心库的单元测试覆盖了提示词内容、回答解析、分类结果映射、分批与取消、错误归类，另有一个本机假服务的测试走通了请求头、去掉参数重试和模型列表。界面在浏览器里用模拟后端检查过设置对话框、写简介、右键菜单和 AI 分类。没有对真实的 AI 服务和系统钥匙串实测过。

### 卸载与残留清理

用户要求“和 Geek Uninstaller 一样，卸载后清理文件夹和注册表”，参考 GitHub 上的开源卸载工具。参考了 Bulk Crap Uninstaller（Windows，Apache-2.0）和 Pearcleaner（macOS，Apache-2.0）的做法，代码是新写的（`crates/core/src/leftovers.rs`）。

| 项 | 说明 |
|---|---|
| 流程 | 已改成先分析再卸载，见下面“卸载前先分析” |
| Windows 找哪里 | 原来的安装文件夹（高）；Program Files 里和软件同名的文件夹（高）、“发布者\软件名”（高）；AppData（Roaming、Local、Local\Programs、LocalLow）、ProgramData 里同名的（中）；开始菜单里同名的文件夹和快捷方式、桌面上同名的快捷方式（中）；名字包含软件名的（低）。注册表：没删掉的卸载项（高）；HKCU、HKLM、HKLM\WOW6432Node 下的 Software\发布者\软件名（高）、Software\软件名（中）；指向原来安装文件夹的 App Paths 项和 Run 开机启动值（高） |
| macOS 找哪里 | ~/Library 下和 bundle id 完全一致的 Application Support、Caches、Containers、HTTPStorages、WebKit、Logs、Application Scripts、Saved Application State、Preferences、Cookies（高）；同一个 bundle id 开头的偏好和 ByHost、LaunchAgents（中、高）；Group Containers 里以它结尾的（中）；Application Support、Caches、Logs 里同名的（中）、“发布者/软件名”的（高，带版本号的低）。苹果自己的应用不找 |
| 名字怎么比 | 只留字母和数字（含汉字）、转小写；去掉版本号、位数、括号里的说明；“Microsoft Edge”还会去掉开头的发布者变成“edge”。英文至少 4 个字符、汉字至少 2 个；Microsoft、Common、Update、Cache 这类泛泛的词不拿来比。“包含软件名”的要求软件名至少 6 个字符，而且对方不能比它长太多 |
| 不碰的 | 别的已安装软件的文件夹、它们里面的、里面装着它们的；和别的已安装软件同名的（卸 Python 3.11 时 Python 3.12 还在，就不动 Python 文件夹）；整个盘、Windows 文件夹、Program Files / ProgramData / 用户文件夹这类公共文件夹本身、发布者文件夹本身、~/Library 本身和它下面的标准文件夹；注册表只允许 Software\软件、Software\发布者\软件（Classes、Policies、Microsoft\Windows 这些不行）、某一个卸载项、某一个 App Paths 项、Run 里的值。删除前按这套规则再查一遍（`allowed`），界面传来的只是上次扫描结果里的序号 |
| 默认勾选 | 高、中可信度默认勾上，低的不勾。卸载程序被取消、软件看起来还在时，全部降成低、一个都不勾，并提示 |
| 怎么删 | 文件和文件夹移到回收站（废纸篓）。注册表先用 `reg export` 导出到本机应用数据目录的 `uninstall-backups/日期-时间/`，导出成功才删；结果里有“打开”备份文件夹的按钮 |
| 管理员权限 | Program Files、ProgramData、HKLM 下的普通权限删不掉，结果里列出来，可以“以管理员身份重试”：把清单写进临时文件，用 PowerShell 的 `Start-Process -Verb RunAs` 提权再启动一次 ShibaPack（带 `--shibapack-cleanup` 参数，只做清理、不开窗口、不受单实例限制），等它做完读回结果。提权的进程同样按 `allowed` 检查每一项 |

验证情况：单元测试用临时文件夹模拟了 Windows 和 macOS 的目录，覆盖了匹配、可信度、不碰的规则和注册表路径的检查；Windows 的代码在这台 Mac 上用 Windows 目标做过类型检查。在这台 Mac 上对 VS Code、Edge、RustDesk、DataGrip 实际只读扫描过，结果合理。界面在浏览器里用模拟后端走通了 Windows 和 macOS 两种流程（含管理员重试）。**没有在 Windows 上实际运行过**：注册表扫描、`reg export`、回收站、UAC 提权都还没实测。可以在 Windows 上用 `SHIBAPACK_LEFTOVER_APP="软件名" cargo test -p shibapack-core scans_real_app -- --ignored --nocapture` 只读地看一个装着的软件会被找出什么。

### 详情栏重排

用户反馈“布局信息很混乱，排版页混乱”。原来的问题：安装状态的两行用了橙、蓝、绿三种文字颜色，两个按钮一大一小；版本是一排标签加一张卡片；每个安装包占两行；“更多信息”里字段上下堆着。现在按块排，块与块之间一样的间距，每块一个小号灰字标题（`SectionHeader`）：

| 块 | 样子 |
|---|---|
| 头部 | 图标、名字、发布者；右边收藏和 ⋯（⋯ 里多了“编辑描述…”） |
| 简介 | 和原来一样，多了“编辑”（自己写描述） |
| 安装状态 | 一张表，至多两行（这台电脑上 / 在线源），每行左边一个图标（只有图标带颜色），中间两行字，右边至多一个按钮，按钮一样大 |
| 版本 | 标题右边两个图标按钮（添加安装包、清理旧版本）；下面一张表，每个版本一行（版本号、默认、本机、文件数和大小、⋯），点一行展开它的安装包，一开始只展开默认版本。设为默认、安装这个版本、备注、改版本号、删除都在 ⋯ 里 |
| 安装包 | 一行：平台图标、文件名（太长从中间省略）、大小；平台和架构在图标的提示里。运行、定位、更多在鼠标停上去时出现 |
| 更多信息 | 默认收起。分类、主页、备注、添加时间排成两列的表（左边名字、右边值，点值就能改）；下面是在线源 |

### 导入窗口、文件夹安装包、文件属性、失败日志

用户要求：文件夹可以当作软件安装包，通过文件夹里的文件判断和取图标；左栏可以直接把安装程序拖进对应的分类；拖进中间一栏时先弹出窗口选当前分类、智能分类等，确认后才导入，窗口不关、显示进度；记录失败日志；导入失败要有具体的错误信息；网格视图悬停显示简介；Windows 的文件版本从文件自带的属性里取并缓存；更新后自动安装没有权限。

| 项 | 做法 |
|---|---|
| 导入窗口 | 从系统拖进中间一栏（或侧栏分类以外的地方）先打开导入窗口：列出每一项（文件的大小和会被认成的软件名、版本；文件夹可以选“作为一个软件”或“里面的 N 个安装包”），分类选当前分类 / 智能分类 / 选择分类 / 不分类，存储方式选复制 / 移动 / 只记录位置。确认后窗口不关，显示进度条，可以停止或“在后台继续”；导完显示导入、重复、失败的个数和失败的文件。选了智能分类时，导完给一个按钮对这次导入的软件打开智能分类的预览 |
| 拖到侧栏 | 拖到侧栏的分类（展开和收起的侧栏都行）上时那一行变色，松开直接导入进这个分类；带着普通文件夹时打开导入窗口，分类已经选好，让用户决定文件夹怎么导。分类只给新建的软件和还没分类的软件，已经分好类的不动（`ImportHint.categoryId`） |
| 文件夹安装包 | `ImportHint.packages` 里的文件夹和所有 `.app` 整个当作一个安装包：哈希按每个文件的相对路径和内容算（内容一样的文件夹算重复），大小是全部文件加起来，托管时整个复制到 `软件名/版本号/文件夹名`（先放进 `.part` 再改名；移动跨磁盘时核对一致才删原文件夹）。扫描文件夹时遇到 `.app` 不往里面走。“像一个软件”的判断：是 `.app`，或第一层有 exe 还带着 dll，或第一层就一个 `.app` |
| 文件夹的信息和图标 | 主程序：`.app` 本身；第一层和文件夹同名的 exe，没有时最大的那个（卸载、更新、崩溃报告程序不算）。版本号、软件名、发布者取主程序的属性（`.app` 读 Info.plist），图标取主程序的，没有时取第一层的 ico / icns / png。“运行”打开主程序，找不到时打开文件夹；“校验”按文件夹里的文件加起来核对大小 |
| 文件属性 | `fileinfo.rs`：exe 读版本信息资源（产品版本优先，没有时文件版本；产品名，没有时文件说明；公司名），msi 读 Property 表（ProductName、ProductVersion、Manufacturer），不依赖 Windows。`1.1.0.0` 整理成 `1.1.0`。导入时文件名里没有版本号就用它；文件名是 setup 这类时用产品名；新建的软件用公司名做发布者。已经导入、版本号是空的（放在 `unknown` 里的）在打开仓库后由 `fill_file_info` 在后台补上：读到版本号就挪到那个版本，托管文件跟着挪文件夹，挪空的 `unknown` 版本删掉。读过的按 SHA-256 记在 `.shibapack/cache/fileinfo.json`（读不出来的也记），同一个文件只读一次 |
| 具体的错误信息 | 导入的每一步标上名字（`read` 读取、`copy` 放进仓库、`save` 登记），系统错误归成几类：没有权限、文件不存在、磁盘满、只读、被占用、文件名太长或不合法、网络磁盘断开、已存在，归不了类的显示系统原话。结果里每个失败的文件写“哪一步出错：原因”，下面是系统原话和完整路径。不是从导入窗口开始的导入（工具栏、拖到侧栏）有失败时也打开这个结果窗口 |
| 失败日志 | `faillog.rs`：每行一条 JSON，放在应用自己的日志文件夹（只和这台电脑有关，不进仓库），超过 1 MB 换一份，最多两份。导入失败、启动项操作失败、更新失败、界面上的出错提示都记一笔。设置里新加“失败日志”页：看最近 500 条、打开文件夹、清空 |

| 扫描 | `crates/core/src/disk.rs`。几个线程一起走：遇到子文件夹时有闲着的线程就交给它，没有就自己接着走，不管哪个文件夹特别大都不会只剩一个线程在干活。大小按实际占用（macOS / Linux 用块数），硬链接只算一次；不跟符号链接，不进别的盘（macOS 跳过 /System/Volumes、/Volumes，Linux 按设备号）。没有权限的文件夹记个数，界面上提示。可以停止 |
| 省内存 | 小于 1 MB 的文件按文件夹合成一项“小文件”；扫完小于 1 MB 的文件夹不留子项。这台 Mac 的用户文件夹：86.8 万个文件、168 GB，树上只留 6 万个节点，7.4 秒（最早按前两层分任务时，一个大项目只有一个线程在走，要 397 秒） |
| 给界面的 | 树留在后端内存里，界面要哪一层就取哪一层（往下 4 层，占这一层不到 0.4% 的合成“其他 N 项”），不重新扫。什么都不存到磁盘 |
| 扇形图 | 一圈是一层，角度是大小；第一层每项一个颜色，往下同色变浅，小文件和其他是灰色。中间写当前这一层（鼠标停着时写停着的那项），点中间回上一层 |
| 矩形图 | squarified 排法，文件夹画成带标题的框，里面再排子项（最多 3 层、框够大才往里画）。上面的路径可以点回任意一层；右边是这一层的列表，颜色和图对得上 |
| AI 解释文件夹 | 用户要求“如果 AI 功能有启用，悬停还可以显示文件夹的作用。数据页单独缓存”。AI 可用时，鼠标在一个文件夹或大文件上停 0.6 秒，提示里加一段“它是什么、能不能删”。一次请求问停着的那项，加上这一层还没解释过的（最多 10 个）。给 AI 的是路径（用户文件夹写成 ~）、大小、文件数、里面最大的几项，不读文件内容。答案单独存在仓库的 `.shibapack/cache/ai-folders.json`（`aicache::FolderCache`，和 `ai.json` 分开，按“系统 + 路径 + 界面语言”记），打开一层时先从这里取，有的话停上去马上显示。“小文件”“其他”不问 |
| 点开文件夹 | 用户问矩形图里的文件夹点了打不开：真的扫描里大于 1 MB 的文件夹都能点进去，打不开的是预览里只写了总大小的模拟文件夹。模拟数据现在给这些文件夹编了子文件夹；真的里面全是小于 1 MB 的东西、没法再分的文件夹，提示里写明“不再往下分” |
| 右键菜单 | 色块、右边列表、空白处（当前这一层）都能右键：进入这个文件夹 / 打开文件、在访达（文件夹）中显示、复制路径、移到废纸篓（回收站）。移走前确认大小和文件数，移走后从树上减掉、重画。扫描的位置本身、系统文件夹、用户文件夹本身和它下面的标准文件夹、应用程序（请用卸载）、仓库、挂载点不能移走，后端再查一遍（`disk::protected`） |

验证情况：核心库新增 7 个测试（大小和合并小文件、取视图和移走后的合计、停止扫描、硬链接只算一次、哪些不能移走、给 AI 的路径把用户名换成 ~、文件夹解释单独一个缓存文件）；在这台 Mac 上只读地扫过用户文件夹、桌面、资源库看速度。预览里用模拟数据走过选位置、扫描进度、扇形图、往里点、矩形图、右键移走（大小减掉、重画）。全部 187 个通过；Windows、Linux 做过类型检查。桌面自检加了 1 项（扫仓库文件夹并取一层），49 项全部通过。**没有实测的**：Windows 上的扫描速度和大小（Windows 用文件大小，不是实际占用）、真的在桌面里移到废纸篓。

### 毛玻璃

用户要求“设置中界面允许支持毛玻璃效果”。

| 项 | 做法 |
|---|---|
| 开关 | 设置 → 通用 → “毛玻璃效果”。只和这台电脑有关，记在界面偏好（`prefs.glass`），不进仓库。浏览器预览和 Linux 上是灰的 |
| 窗口 | 窗口一直是透明的（`tauri.conf.json` 的 `transparent`，macOS 要打开 `macOSPrivateApi`，Cargo 里 tauri 加 `macos-private-api`）。打开时 `set_window_glass` 让系统加效果：macOS 是 `UnderWindowBackground` 的 vibrancy（窗口不在前面时跟着变淡），Windows 是 Mica（Windows 11 才有）。关掉时去掉效果，界面画不透明的底色，和以前一样 |
| 界面 | 系统确认打开了才在 `<html>` 上加 `data-glass`，把 `--bg`、`--bg-side` 换成半透明，模糊透出来。菜单、对话框仍用不透明的 `--panel`；浮在内容上的详情栏用新的 `--bg-solid` |

验证情况：桌面自检加了 1 项（打开、关掉都成功），50 项全部通过。**没有实测的**：打开后的实际观感（自检只确认系统接受了效果）、Windows 11 的 Mica、Windows 10 上打开时的样子（系统不支持 Mica，应该只是没有效果）。
